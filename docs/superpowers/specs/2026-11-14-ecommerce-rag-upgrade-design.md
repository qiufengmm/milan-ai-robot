## 阶段一：验收并收敛分片上传

先验证以下行为，再接入第二套索引：

1. 参数校验：MD5 格式、文件名、总大小、总分片数与分片序号一致；拒绝越界和路径穿越。
2. 正常上传：乱序分片可正确合并，重复分片不重复计数，并发请求不会生成重复记录。
3. 断点续传：返回实际已存在的分片；缺片不得合并；前端取消、恢复和失败重试行为一致。
4. 合并校验：核对最终大小和实际 MD5；重复或并发合并只保留一份结果，并正确触发异步向量化。
5. 生命周期：秒传能区分已就绪、处理中和失败；异常不能被当成知识库可检索成功。
6. 删除协调：保留已有文件归属隔离、后台处理行锁和异常状态保护，验证删除与处理并发时没有孤儿向量。
7. 存量迁移：保留原文件 ID、路径和向量关联；状态仅转换一次，脚本再次执行不改变状态。测试在隔离数据库或隔离 schema 中进行。

文件清理限定在当前上传任务实际拥有的明确路径；执行过程中遵守用户禁止批量删除文件和目录的约束。

## 阶段三：RRF 与 Rerank

检索链路为：选中知识库 → 并行向量召回 / BM25 召回 → 按文档 ID 去重并进行 RRF 融合 → Rerank → 截取 TopN → SSE 回答。

- 向量路和关键词路各取 10 条，RRF 保留 10 条，作为教程初始配置；最终 TopN 独立配置并通过电商题集验证。
- RRF 使用名次融合，不直接相加不同检索系统的原始分数。
- 使用教程中的 `qwen3-rerank`，该模型已在当前账号完成小样本检测；模型名、地址、超时均可配置，不自动认定教程列出的其他模型都有权限。
- Rerank 的返回下标用于重新排列原文档，保留文件和知识库元数据；异常下标、重复下标及无效响应均需处理。
- ES 不可用时，允许在同一知识库内退回向量检索；Rerank 不可用时，退回已融合的排序。日志与评测结果记录实际使用的模式，避免把降级回答标成完整混合检索结果。
- 记录召回、融合、重排和模型生成等阶段耗时；搜索准备耗时、首字耗时和完整回答耗时分开统计。

## 阶段四：多知识库与个性化

### 知识库管理和客服身份

- 创建默认商城知识库，支持列表、新建和编辑知识库名称、说明。
- 商城保留现有商品、配送、售后规则和客服风格。自建知识库使用自身名称与场景，避免始终自称商城客服。
- 人工渠道、期限和政策等事实来自当前库资料；资料不足时的指引也应与当前场景匹配。
- 知识库切换时清楚区分当前聊天和文件列表所属范围，避免前端将先前库的回答继续当成新库上下文。
- 本阶段实现业务知识库隔离；不据此宣称已经具备用户权限或多租户鉴权。

### 上传、续传与检索的完整归属

- 从上传检查/创建任务时确定知识库归属，不能只在合并时临时打标。
- 秒传判定和续传会话至少按「知识库 ID + 文件 MD5」区分；分片按具体上传任务隔离。
- 同一文件可分别属于两个知识库，各自拥有文件记录、向量和 ES 文档；删除一个归属不会清掉另一个。
- PGVector 元数据和 ES 字段统一使用 `knowledge_base_id`，写入与查询类型一致。
- 两条召回路必须在召回前过滤知识库；未选择时明确使用默认商城库，业务聊天请求不得因空 ID 退化为全库查询。
- 文件列表、详情、合并、删除和重建也需验证归属，不只过滤聊天检索。

### 迁移和存量资料

- 保留 `milan_ecommerce` 和原 `robot` 库的现有数据与备份。
- 当前电商文件及向量归入默认商城库，保留原文件 ID 和向量关联；以迁移前后数量、归属检查验证。

## 验收与交付

- 上传：正常、乱序、重复、并发、断点续传、缺片、校验失败、重复合并和并发删除。
- 迁移：已有数据迁移一次成功，重复执行不改变状态或归属，失败可回滚。
- 检索：RRF 去重与排序、真实中文关键词召回、两路按库过滤、Rerank 响应处理和降级。
- 隔离：两个库配置不同退款政策，同一问法只使用所选库资料；相同文件分别上传、续传与删除互不干扰。
- 数据一致性：上传或删除中断、ES 写入失败与恢复后可核对两侧索引，不留下无归属文档。
- 回答：沿用 60 题并增加隔离和故障场景。保存完整召回正文、文档 ID、库 ID、各阶段名次与回答，分别判断检索和回答质量。
- 对比：在同一模型、同一温度、同一语料与题集下重跑纯向量基线和新链路；旧结果保留为历史，不作为本次提升证明。
- 后端测试与构建、前端构建、真实模型和真实数据库/ES 集成验证分别记录，不用单元测试代替真实联调。
