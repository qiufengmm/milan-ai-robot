## 1. 范围锁定与审查结论

只实现整体方案第3节的管理员、HR / IT维护者、普通员工流程，以及第10节的端到端验收。超出该流程的建议记录为范围外，不自动转成待办。

原方案的主要问题及修正：
- 新增六张表及独立问答轮次模型过大：改为四张新表，问答状态和来源直接扩展现有消息表。
- 全部API、页面、DTO改名没有必要：复用 /customer-service 和 /chat 的管理/历史接口，只停用旧自由生成入口。
- 复杂发布生命周期超过“更新资料”的需要：只保留草稿、当前版、历史版、发布、撤回和替换。
- 来源设计过重：只展示实际参考文档/片段，已有真实定位则使用，不建预览器或逐句引用校验引擎。
- 审计、限流、监控各成独立子系统：移出本期，保留基础认证、CSRF、归属、输入/上传校验和安全显示。
- 100题、三组消融、30份语料作为硬性条件过大：改为先跑6个流程用例，再做一轮60用例默认链路评测。
- 反馈后台功能过多：改为“问题说明＋维护者处理”，嵌入知识管理界面，不做统计平台。

## 2. 全局约束

- 按本计划实施业务源码、测试、配置和SQL；不扩展到计划范围外的功能。
- 当前未提交的上传/日志修复以及本地教程保持原样；不能归入本次已完成任务。
- 新企业库和ES索引与旧库隔离，复用现有PG/ES服务。
- 不批量删除文件或目录；多文件清理列出路径交给用户手动处理。
- 不迁移旧电商/通用会话给新员工；不为旧库写通用升级器。
- ADMIN / USER加库READER / EDITOR足够，不建部门树或额外岗位权限体系。
- 身份、会话归属、库读写和发布状态必须由后端判断；管理员也没有浏览所有私人会话的入口。
- 来源文件、会话、历史、反馈都从有归属的记录反查，不能信任客户端提交的userId或role。
- 本期不做SSO、多租户、文档级ACL、OA操作、自动工单、自动反馈入库。
- 不做独立审计表、限流配额服务、效果看板、压测或算法消融。
- 不做定时发布、自动过期、版本比较、回滚和通用文件预览。
- 测试以真实权限/状态/来源边界为主；不为文案、组件改名增加镜像测试。实施期间运行定向后端测试、前端测试与构建；真实数据库及模型评测须单独记录。
- 简历只能反映完成的功能和新评测实际数字，不能沿用旧联网/电商成绩。
