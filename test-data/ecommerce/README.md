# 米兰数码商城 · 电商客服知识库（演示数据）

本目录是「米兰 AI 智能对话平台」智能客服模块的**电商场景知识库**，用于把通用的客服演示改造成「基于私有知识库的电商商品咨询与售后问答系统」。

## 1. 免责与边界

- **米兰数码商城是虚构店铺**。文中商品型号、参数、价格、时效、政策条款、客服邮箱均为**演示数据**，不对应任何真实商家；`support@milan-digital.example.com` 使用的是保留域名 `example.com`，不会真实收信。
- 知识库只放商品资料、服务规则与操作说明，不含真实个人信息、实际订单号或实时订单状态。
- 项目框架、技术栈、数据库表结构、接口与 SSE 协议均未改动；本目录只增加数据、评测与简历材料。

## 3. 与现有解析器的适配约定

这些约定是为了让知识块**不被切碎、不丢字**，改动知识库时请遵守：

1. **用 `---` 明确知识块边界**。`MarkdownReader` 配置了 `withHorizontalRuleCreateDocument(true)`，遇到水平线会结束当前文档；读取器也可能在标题等节点切分，不能依赖跨段上下文。
2. **避免把规则写成引用块 `>`**。`withIncludeBlockquote(false)` 会把引用内容分成独立文档，而非丢弃文字；可能使条件脱离对应问答。
3. **避免使用代码围栏存放规则**。`withIncludeCodeBlock(false)` 同样把代码块分为独立文档。问答正文优先使用普通文本。
4. **每块自包含**：块内必须重复商品型号或政策主题，不写「同上」「见上条」，也不依赖标题——标题会进 `metadata.title`，正文才是被向量化和被模型看到的内容。
5. **单块控制在 350 字以内**。监听器在解析后还会过一遍 `TokenTextSplitter`（默认 800 token），块过大时规则条件可能被切到下一个块里。
6. **条件与例外写在同一块**。「拆封能不能退」这类问题必须把适用条件、例外情形、运费承担一次写完，否则模型只能看到半条规则。

## 4. 入库方式

### 4.1 前置条件

```bash
# 独立演示库（不碰原 robot 库）
psql -U postgres -c "CREATE DATABASE milan_ecommerce;"
psql -U postgres -d milan_ecommerce -f sql/schema.sql
```

`application-dev.yml` 的 `datasource.url` 已指向 `milan_ecommerce`；`application-secret.yml`（本地、已 gitignore）提供 `api-key` 与 `base-url`，向量化模型为 `qwen3.7-text-embedding-flash`（1024 维）。

### 4.2 走现有上传流程

页面上传：进入「智能客服」页面 → 右上角设置 → 上传 `.md` 文件。
或直接调用接口（multipart 字段名固定为 `file`）：

```bash
for f in test-data/ecommerce/0[1-9]-*.md test-data/ecommerce/10-*.md; do
  curl -X POST -F "file=@$f" \
    http://localhost:8080/customer-service/md/upload
done
```

上传接口立即返回记录 id，向量化由 `AiCustomerServiceMdUploadedEvent` 异步完成：状态依次为 `0 待处理 → 1 向量化中 → 2 已完成`（失败为 `3`）。向量 ID 由「文件记录 ID + 正文」共同生成：同一记录后台重试保持幂等，不同上传记录拥有独立向量。重复上传会新建文件记录，替换文档时需显式删除旧记录，避免旧版本继续参与检索。文件归属行在向量化事务内加锁，强制删除会等待正在执行的事务结束；已被删除的记录不会继续写入向量。空白文件或扫描 PDF 没有可提取文字时标为失败，扫描件需先进行 OCR。

2026-10-21 的归属隔离修复只作用于新处理的文件；已有向量不会自动改写。若旧版本曾因重复正文发生归属覆盖，需要逐个删除受影响记录后重新上传各自源文档；本地备份保留供恢复。

若原有 01–05 文件已导入，只补充上传新资料，可运行：

```bash
for f in test-data/ecommerce/0[6-9]-*.md test-data/ecommerce/10-*.md; do
  curl -X POST -F "file=@$f" \
    http://localhost:8080/customer-service/md/upload
done
```

### 4.3 入库校验（实际执行过）

```sql
-- 文件处理状态：应为 2（已完成）10 条
SELECT id, original_file_name, file_size, status FROM t_ai_customer_service_md_storage ORDER BY id;

-- 按文件统计知识块与向量：每块都应有非空 embedding
SELECT metadata->>'originalFileName' AS file, count(*) AS chunks, count(embedding) AS with_vec,
       min(length(content)) AS min_len, max(length(content)) AS max_len
FROM t_vector_store GROUP BY 1 ORDER BY 1;

-- 文件关联元数据是否完整
SELECT metadata->>'mdStorageId' AS id, metadata->>'title' AS title
FROM t_vector_store LIMIT 5;
```

## 6. 评测

- 题集：eval/eval_questions.json，共 60 题：45 道需要知识库作答、6 道条件不明确、2 道政策缺失、1 道超出资料范围、6 道未接入能力。C01「你们卖显示器吗？」已改标为知识库可回答，因为目录块明确列出四类在售商品。
- 当前运行条件：模型 deepseek-v4-flash-0731、温度 0.0、topK=3、2026-10-20 导入的 10 个知识库文件。
- 执行脚本：eval/run_eval.py。按题调用客服 SSE 接口，并从应用日志记录回答全文和每个检索块“常见问法”前 70 个字符。
- 当前模型 60 题全部得到非空回答，逐题人工复核为 **52 题完全正确（86.7%）、8 题部分正确、0 题错误或无回答**；51 道适用题的 top-3 检索预览均包含相关线索，另 9 题不适用检索判定。该指标基于前 70 字符预览，不能替代完整知识块召回核验。详见 [逐题复核报告](eval/results_60_deepseek-v4-flash-0731_20261020-200355_quality_report.md)。
- 平均耗时 13.2 秒、中位数 9.93 秒（含重试与等待）；A03、A04、B02、B05 共发生 6 次 TLS 握手失败，66 次尝试后最终 60 题均有回答。逐次原因由当次应用日志对齐补充到 JSON；评测脚本本身记录尝试次数和最终异常。运行记录见 `eval/results_60_deepseek-v4-flash-0731_20261020-200355_report.md`。
- 部分正确样例包括 A02 过度追问、B03 漏设备/线材条件、C03 无关订单指引、D02 推断未知订单、E11 漏地区总时效、E15 缺少必要追问、E17 未确认原支付渠道、E18 未引导查看商品页。
- 历史 deepseek-v4.1-flash 的 60 题结果保存在 `eval/results_60.json`：55 题完全正确、4 题部分正确、1 题无回答。模型已切换，两轮成绩不能直接表述为准确率提升。
- 原 42 题基线保存在 `eval/results.json`：40 题完全正确、2 题部分正确。该结果只代表旧题集和旧知识库版本，不应当作扩充后 60 题的成绩。
- 简历描述见 resume-description.md。当前评测不支持宣称线上准确率、延迟 SLA 或准确率提升。
## 7. 当前限制（真实情况，不是"后续规划"）

1. **客服是单轮的**。`/customer-service/chat/completion` 只读 `message`，请求里的 `chatId` 未参与业务，也没有挂对话记忆 Advisor 与消息落库 Advisor。刷新或追问「那保修呢」时没有上下文。多轮记忆与消息持久化只存在于通用对话 `/chat/**`。
2. **没有接入任何业务系统**。查不到订单、物流、库存、支付与退款状态，也不能退款、取消订单、改地址、建工单、转人工。提示词要求不假装查询，但这不是程序化保证，也不提供查询能力。
3. **检索是固定 topK=3 的纯向量相似度**，没有相似度阈值、没有关键词/混合检索、没有重排序、没有查询改写。问法与知识块措辞差异过大时可能召回不到。
4. **提示词是回答策略，不是确定性校验**。它降低越界与幻觉概率，但不等于政策规则引擎或幻觉拦截系统，仍可能出现过度追问、漏掉地区时效、没有明确追问必要条件或资料不足时给出不相关指引等问题（见当前复核报告中的 A02、E11、E15、C03）。
5. **政策条款没有程序化校验**。所有条件（7 天、99 元包邮、12 个月保修）都以文本形式存在，模型可能漏说例外条件。
6. **本轮评测是本地演示结果**。60 题使用 2026-10-20 核验的 10 份文件与 100/100 非空向量；本地 `eval/milan_ecommerce_backup_100_20261020.sql` 为 100 向量备份，较早的 `eval/milan_ecommerce_backup.sql` 只有 59 个向量，两份均不上传 GitHub。Docker Desktop 曾因 containerd SIGBUS 退出，模型请求也出现过 TLS 中断，因此评测耗时不代表稳定服务 SLA。

## 8. 超出本次范围的建议

以下能力本次**未实现**，仅作为后续方向列出，简历与演示中不得表述为已具备：

- 订单/物流只读查询：需要新增订单、物流业务表与接口，属于新增业务域，不在本次改造范围
- 售后操作闭环（退款、取消、改地址、工单）：需要业务系统对接与权限体系
- 会话记忆与客服消息落库：可复用已有的 `CustomChatMemoryAdvisor`、`CustomStreamLoggerAndMessage2DBAdvisor`
- 检索优化：相似度阈值过滤、问题改写、重排序、混合检索
- 知识库运营：失效政策巡检、答案质量回归、用户反馈闭环
